# Native app model

Apps created with `--tizen-language native` contain no Tizen-specific source code. You write only Dart code, and your app runs on a **prebuilt C++ runner** provided by flutter-tizen. The runner is the same C++ embedding used by C++ apps, so native apps behave exactly like C++ apps on emulators and devices.

|                                    | `csharp`                     | `cpp`                                   | `native`                                   |
| ---------------------------------- | ---------------------------- | --------------------------------------- | ------------------------------------------ |
| Tizen code in your project         | `App.cs`, `Runner.csproj`    | `src/runner.cc`, `inc/runner.h`, ...    | None (manifest, icons, and optional configuration) |
| Runner                             | Built from your project      | Built from your project on every build  | Prebuilt by flutter-tizen                  |
| C++ plugins                        | Supported                    | Supported                               | Supported (`libflutter_plugins.so`)        |
| C# plugins                         | Supported                    | Not supported                           | Not supported                              |
| TV devices                         | Supported                    | Not supported                           | Not supported                              |

Use the native model if you don't need custom native code in the runner. Window settings can be supplied in `tizen/flutter-tizen.yaml`. For custom lifecycle callbacks or other native code, use `--tizen-language cpp` instead.

## Create an app

```sh
# A UI app.
flutter-tizen create --tizen-language native my_app

# A headless service app.
flutter-tizen create --tizen-language native --app-type service my_service_app

# A package with both a UI app and a service app.
flutter-tizen create --tizen-language native --app-type multi my_multi_app
```

`--tizen-language native` is only available for apps. Plugins and modules still use `cpp` or `csharp`.

Build and run the app as usual:

```sh
cd my_app
flutter-tizen run
flutter-tizen build tpk --release
```

## Project structure

```
my_app/
├── lib/
│   └── main.dart
├── pubspec.yaml
└── tizen/
    ├── shared/
    │   └── res/
    │       └── ic_launcher.png
    └── tizen-manifest.xml
```

The `tizen` directory contains only files you own. Files generated by flutter-tizen (such as the Dart entrypoint with the plugin registrant and the packaging directory) are kept in `.dart_tool/tizen`.

The following directories in `tizen` are optional and packaged with the app:

- `shared`: Copied to `shared` of the TPK.
- `res`: Copied to `res` of the TPK.
- `lib`: Shared libraries (`*.so`) are copied to `lib` of the TPK. Libraries for a specific architecture can be placed in a subdirectory named after it (`arm`, `arm64`, `x86`, or `x64`, or the Tizen names `armel`, `aarch64`, `i586`, or `x86_64`), and only those matching the build target are packaged.

A file generated by flutter-tizen takes precedence over your file of the same name in `res` and `lib`.

## Configure the app

Configure the package ID, version, `api-version`, label, icon, privileges, and features in `tizen/tizen-manifest.xml`. See [Tizen manifest](https://docs.tizen.org/application/tizen-studio/native-tools/manifest-text-editor) for the full reference.

`type="flutter"` on the application elements marks the app as a native app. flutter-tizen changes it to `type="capp"` in the built TPK, so the platform launches (and debugs) the app with the native app loader, exactly like a C++ app. The `exec` attribute is the file name under which flutter-tizen installs the runner in the package (`bin/<exec>`).

The runner also reads the following metadata:

| Key                                                         | Description                                                                          |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `http://tizen.org/metadata/flutter_tizen/dart_entrypoint`   | The Dart entrypoint function of the application. Defaults to `main`.                |
| `http://tizen.org/metadata/flutter_tizen/enable_impeller`   | `false` to disable Impeller (enabled by default).                                   |
| `http://tizen.org/metadata/flutter_tizen/enable_flutter_gpu`| `true` to enable Flutter GPU.                                                        |

A Dart entrypoint other than `main` must be annotated with `@pragma('vm:entry-point')` so that it's not removed in release builds.

### Window configuration

Native apps can optionally provide `tizen/flutter-tizen.yaml`:

```yaml
configuration:
  window_offset_x: 0
  window_offset_y: 0
  window_width: 0
  window_height: 0
  transparent: true
  focusable: true
  top_level: false
  user_pixel_ratio: 0
  pointing_device_support: true
  floating_menu_support: true
```

Only specified values are applied, before `FlutterApp::OnCreate()` creates the
window. If the file, `configuration` section, or a property is absent, the runner
keeps its existing defaults: offsets and dimensions `0`, transparent `false`,
focusable `true`, top-level `false`, pixel ratio `0`, and both input flags `true`.
The example explicitly enables transparency. A dimension of `0` uses the screen
size; a pixel ratio of `0` uses the device pixel ratio.

Offsets must be signed 32-bit integers, dimensions non-negative 32-bit integers,
pixel ratio a finite non-negative number, and flags YAML booleans (`true` or
`false`). Invalid values and unknown configuration properties fail the build.

The configuration applies to UI applications in the package; service applications
have no window and ignore these settings. During packaging, flutter-tizen adds the
specified settings as metadata to the packaged UI application elements, replacing
any metadata with the same keys. Your source manifest is not modified. Rebuild
and reinstall the TPK after changing the configuration; hot reload does not apply
window settings. The runner binary is still shared and cached across apps.

`top_level: true` requires the
`http://tizen.org/privilege/window.priority.set` privilege in the manifest.
Pointing device and floating menu settings only have an effect on TV; adding these
settings does not add TV support to the native app model.

### Multi apps

In a multi app, both applications are declared in a single manifest. They share the same Dart code and differ in their entrypoints:

```xml
<ui-application appid="com.example.my_multi_app" exec="runner" type="flutter" ...>
    ...
</ui-application>
<service-application appid="com.example.my_multi_app_service" exec="runner_service" type="flutter" ...>
    ...
    <metadata key="http://tizen.org/metadata/flutter_tizen/dart_entrypoint" value="serviceMain"/>
</service-application>
```

The runner uses `FlutterServiceApp` (headless) for `service-application` elements and `FlutterApp` for `ui-application` elements.

## How it works

When you build a native app, flutter-tizen:

1. Compiles your Dart code and assets, like for any other app.
1. Builds the C++ plugins used by the app into `libflutter_plugins.so`, together with a generated `FlutterRegisterPlugins` function which registers all plugins. Nothing is built if the app uses no C++ plugins.
1. Takes the prebuilt runner and copies it to `bin/<exec>` for every application in `tizen-manifest.xml`.
1. Packages everything with your `tizen-manifest.xml` (with `type="capp"`) and the files in the `shared`, `res`, and `lib` directories into a TPK and signs it with your certificate profile.

No runner code is compiled as part of your app build. The runner is built from [`embedding/cpp/runner`](../embedding/cpp/runner) only once for each target configuration (rootstrap, device profile, and build mode) and cached in `flutter/bin/cache/artifacts/tizen-runner`. The cache is updated automatically when flutter-tizen is updated, and when the rootstrap or toolchain definitions of the Tizen SDK change.

At startup, the runner:

1. Reads the application type and the Dart entrypoint from the manifest.
1. Starts the Flutter engine with `FlutterApp` or `FlutterServiceApp`.
1. Loads `lib/libflutter_plugins.so` if it exists and calls `FlutterRegisterPlugins`.

## Troubleshooting

- To see the runner logs, run `sdb dlog ConsoleMessage`. If a plugin cannot be loaded, the runner logs `Could not load .../libflutter_plugins.so` and the app exits.
- To force a rebuild of the runner, for example after a Tizen SDK update that changes none of the rootstrap or toolchain definitions, delete the `flutter/bin/cache/artifacts/tizen-runner` directory.

To migrate an existing C++ or C# app, see [Migrating to the native app model](migrate-to-native-app.md).
